# 邮件助手多人版

本分支增加邮箱＋密码登录，受邀注册。每个账号有独立的邮件数据库、设置、重要事项和后台收信进度。QQ 授权码和 AI Key 使用服务器密钥加密保存。登录密码使用 scrypt 哈希，不保存明文。

根目录 `app.py` 是启动入口，具体代码在 `backend/app.py`，仍支持单人 Mac 模式。多人版通过根目录 `cloud.py` 启动，具体代码在 `backend/cloud.py`，不读取原来的邮件库或 macOS 钥匙串。

## 每个人连接自己的日历

每位用户登录后，在“连接设置 → 日历”选择“Apple 日历”或“Outlook 日历”，点击“连接”。系统会为该账号生成专属的订阅链接。按所选日历的说明添加这个订阅链接一次，之后用户在邮件助手中逐条核对并点击“加入日历”的日程，就会出现在自己的“邮件助手”订阅日历中。未确认的邮件日程不会进入订阅。不同账号的订阅内容互相隔离。

这是一种**只读日历订阅**，不会直接写入用户已有的主日历，也不能检测用户是否完成了订阅。更新速度由日历应用决定，不能保证立即显示。链接相当于只读访问凭证，不要公开分享。完成外部订阅后，用户可点击“我已完成订阅”；界面显示“已确认订阅”，这是用户确认，不是系统自动验证。更换日历会重置此确认。想要单次手动导入，可在日程确认窗口的“更多”中选择“导出日历文件”。

本机预览生成的是 `127.0.0.1` 链接，只有运行程序的电脑能访问；手机或其他同学必须等网站部署到有 HTTPS 的公开地址后才能订阅。Apple 日历可使用订阅链接；其他日历服务是否支持私有订阅链接，需要在目标服务上单独验证。若将来要求直接写入各人的主日历，需要再做对应服务的账号授权连接。

## 重复通知与更新通知

加入截止事项或确认加入日程时，会对照已加入的同类事项。内容一致的重复通知直接关联已有卡片；可能有更新或主题相似的通知会显示字段差异，由用户选择更新并合并、保留原内容合并或另建事项。人工修改过的字段默认不勾选替换，空白或待确认信息不会用于覆盖已知信息。收到或分析邮件本身不会更新已有卡片。

一张卡片可以关联多封来源邮件。移除卡片会解除这些关联，各封邮件恢复为可加入状态。订阅日历沿用已有日程并更新内容，不增加第二条日程；外部日历需要等待订阅刷新。本机直接写入 Apple 日历的模式目前只会更新事项卡片，外部日程需手动修改，核对窗口会提示这一限制。

## 本机预览

依赖安装后可运行 `.venv/bin/python preview.py`，自动在被 Git 忽略的 `cloud-data/development.secret` 中创建本机开发密钥。此启动器只监听本机，不用于公网部署。

## 本地启动

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-cloud.txt
```

首次生成一个独立密钥，妥善保管，不要提交到 Git：

```sh
.venv/bin/python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

把生成结果配置为环境变量 `MAIL_MASTER_KEY`。每次启动必须使用同一个密钥，丢失后无法解密已保存的邮箱和 AI 凭证。生产环境应存入托管平台的秘密变量，备份密钥与数据分开保管。

```sh
export MAIL_MASTER_KEY='这里填写生成的密钥'
.venv/bin/python cloud.py serve
```

访问 `http://127.0.0.1:18744`。原单人版仍使用 18743。

## 邀请和账号恢复

使用同一组环境变量生成绑定邮箱、7 天有效、一次性的专属注册链接：

```sh
.venv/bin/python cloud.py invite --email classmate@example.com
```

命令输出完整注册链接。把链接私下交给对应同学；同学点开后邮箱自动填写，只需设置密码。链接绑定邮箱、7 天有效且只能注册一次；打开链接不会消耗邀请。链接中的邀请凭证放在 # 后，不进入普通页面请求，并在页面读取后从地址栏移除；刷新后若需继续注册，请重新打开原链接。当前未接通邮箱验证，管理员需事先核实邮箱，持有链接本身不证明邮箱所有权。不要公开链接。

忘记密码时，管理员先通过已知联系方式核实本人，再生成 30 分钟有效的一次性重置码：

```sh
.venv/bin/python cloud.py reset --email classmate@example.com
```

用户在“忘记密码”中输入。重置后旧登录状态全部失效。已登录用户可在“账号”中修改密码或退出。浏览器可保持登录 30 天。

## 部署边界

- 以下是部署要求；实际运行状态以托管平台为准。
- 公网需要 HTTPS，设置 `MAIL_ORIGIN=https://你的域名`、`MAIL_BIND=0.0.0.0`、`PORT`，反向代理保留正确 Host。
- `MAIL_DATA_DIR` 指向持久化磁盘，默认 `cloud-data`；禁止使用会在重启时丢失的数据盘。
- 只运行一个应用进程，启动时使用文件锁避免重复后台收信。适合第一批小规模用户，不支持多副本负载均衡。
- 后台每分钟检查，每人单独任务和游标；登录退出不影响后台收信，重启会恢复已开启状态。邮箱或 AI 出错时会暂停该用户自动分析，由用户查看后重新开启。
- 当前多人版限制为预设服务商接口，不能填写任意自定义服务器地址。
- 上线前仍需在目标服务器验证 QQ IMAP 可达、模型服务可达、HTTPS、持久化、备份恢复和手机日历订阅。
- 邮件正文保存在服务器数据盘，管理员在技术上可访问；凭证加密也不是端到端加密。邀请同学前需明确告知数据存放位置和使用方式。
- 尚未接通验证邮件、自助邮件找回；本阶段采用管理员核实身份、定向邀请和重置。

## Railway 首次部署

1. 在 GitHub Desktop 把本分支新增的 `Dockerfile`、`.dockerignore`、`cloud.py`、测试和本文提交并推送。Railway 需要从 GitHub 读取这些文件。
2. 在 Railway 建立项目，选择 **GitHub Repo** → 私有仓库 `campus-mail-assistant`，在服务设置中把部署分支选为 `feature/multiuser`。仓库根目录的 `Dockerfile` 会安装多人版依赖并以单进程启动。
3. 给此服务连接 **Volume**，挂载路径设为 `/data`。Railway 会提供 `RAILWAY_VOLUME_MOUNT_PATH`，程序将其作为账号、邮件和进度的数据目录；缺少 Volume 时程序会拒绝启动。只保持一个副本。
4. 在服务 **Settings → Networking → Public Networking** 点 **Generate Domain**。Railway 提供 HTTPS 域名；程序会自动采用该域名作为站点地址。若以后换为自定义域名，在服务变量里设置 `MAIL_ORIGIN=https://你的域名`，并确认原日历订阅链接要重新设置。
5. 在服务 **Variables** 添加 `MAIL_MASTER_KEY`，值是用上文 Fernet 命令生成的一条新密钥。它与本机预览密钥分开，不放在 GitHub，也不要发在聊天中。保存后另行备份；丢失会导致已有授权码与 API Key 无法解密。无需手动设置 `MAIL_DATA_DIR`、`MAIL_BIND` 或 `PORT`。变量变更要应用并重新部署。
6. 确认部署状态正常并能打开登录页，再通过 Railway CLI 的 `railway ssh` 进入运行中的服务，运行一次 `python cloud.py invite --email 你的注册邮箱` 生成个人注册链接。链接只发给对应的人。先用本人账号验证 QQ IMAP、AI 分析、手机访问和日历订阅，之后再邀请同学。

首次创建服务时，在域名、Volume 和密钥准备好之前出现启动失败是预期的；三者配置完成后重新部署即可。试用方案的对外端口限制可能影响 QQ IMAP 的 993 端口，因此要在实际运行方案上验证云端收信。开始长期使用前配置 Volume 备份，并定期确认可恢复；不能只依赖 GitHub 备份用户数据。

## 验证

```sh
.venv/bin/python -m unittest discover -s tests -v
```

覆盖账号隔离、邮件及重要事项隔离、凭证加密、来源与跨站请求检查、退出、重置失效、登录限流、接口地址限制、重启后游标和自动分析状态恢复。不发送真实邮件、不调用付费模型。

## 修改在哪里

本机文件 → 测试 → Git 提交 → 推送 GitHub → 部署服务器。

GitHub 保存代码版本；运行中的网站只有完成部署才更新。这个分支 `feature/multiuser` 与原本 `main` 分开，确认后再合并。

## 中文原邮件展示

点击“中文”后才翻译。翻译只替换原邮件中的文字段落，保留列表、表格、链接地址和图片位置，不让模型生成 HTML。中文与原文使用同一隔离阅读器，外部图片仍需手动加载。译文按原文内容和格式版本缓存，旧纯文本缓存会自动失效；返回段落不完整时不保存残缺译文。
